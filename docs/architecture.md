# Sula 架构

Sula 是单机桌面应用：React 展示资料库和任务状态，Tauri 提供本地调用边界，Rust 处理扫描、刮削、数据库和文件变更。界面不直接操作 SQLite 或系统凭据。

## 模块职责

| 模块 | 负责 | 不负责 |
| --- | --- | --- |
| `desktop/src` | 页面、选择与筛选、交互反馈、国际化 | 原生文件操作与密钥持久化 |
| `desktop/src-tauri` | commands/events、窗口、托盘、配置、共享状态、任务队列；`src/app` 应用服务层 | 在界面层复制媒体领域规则 |
| `media-core` | 媒体模型、扫描、文件归属、SQLite、NFO、图片缓存 | 外部数据源搜索与 UI 状态 |
| `scraper-kit` | 数据源请求、候选匹配、返回元数据与图片字节 | 数据库、NFO 与图片写入；系统窗口与页面布局 |
| `renamer` | 命名模板、批量规则、预览、执行、撤销与媒体变更恢复 | 用户界面和数据源账号管理 |

## 主要调用路径

```text
React 组件 → Zustand 操作 → Tauri command → Rust 应用状态 → 领域模块
                                     ↑              ↓
                              任务事件 / 查询结果 ← 任务队列与数据库
```

资料库加载通过分页命令读取条目及摘要，前端再进行筛选、排序与虚拟列表渲染。详情与海报按需要加载；海报请求经过前端队列和缓存，再调用原生缩略图能力。

扫描先确认资料库根可访问及身份一致，再依据目录状态决定增量枚举范围。无法读取目录不等于媒体已删除。NAS、符号链接、共享目录和目录替换涉及不同边界，不能仅凭路径存在就判断文件归属。

刮削由 coordinator 按媒体类型和可用凭据选择数据源，搜索候选并判断能否自动接受；无法确定时交给手动匹配。scraper-kit 只返回数据；NFO、图片和数据库写入由应用服务层完成，可能分别失败，界面需要呈现部分完成状态。

文件整理同时涉及磁盘与数据库，不能用单一数据库事务代表全部成功。媒体路径变更通过操作记录和恢复逻辑处理；启动时会尝试恢复未完成操作，未解决的恢复问题可阻止后续变更。

## 状态与生命周期

- `AppState` 持有数据库、配置、任务队列、缓存和重命名服务；数据目录使用进程锁防止同一库被多个实例同时写入。
- `ConfigStore` 管理配置文件与系统凭据引用；写入失败需保留原配置和仍有效的凭据。
- 任务取消为合作式取消，不等于撤销此前已经完成的文件或数据库变更。
- Zustand 保存界面状态并接收任务事件；异步切换资料库和条目时应避免旧响应覆盖当前选择。
- 关闭窗口与退出进程不同，行为由托盘和“关闭后继续运行”配置决定。

## 应用服务层

`desktop/src-tauri/src/app` 承载命令背后的业务流程，不依赖 Tauri 类型，可用临时目录、内存数据库和假实现直接测试。`commands.rs` 只负责解析参数、选择锁范围、入队任务、调用服务和映射结果；IPC 命令、参数、返回结构和事件保持不变。

| 模块 | 内容 |
| --- | --- |
| `app/mod.rs` | `TaskProgress`；`Progress` trait（进度、刮削计数、取消标志），由任务队列的 `TaskHandle` 实现；`Events` trait（`library_updated`），由 `AppHandle` 实现 |
| `app/scrape.rs` | `ScrapeService`：资料库刮削、条目刮削与重刮、单季刷新、手动匹配，以及其后的自动重命名或合并；`MetadataSource` trait 抽象网络端，正式实现为 `scraper_kit::ScrapeClient` |
| `app/scrape_persist.rs` | 刮削结果落盘：元数据与季集入库、NFO、海报与剧照文件、`owns_folder` 检查、问题汇总为 `Partial` 状态并脱敏 |
| `app/library.rs` | `RefreshService`：资料库与条目刷新、刷新后合并重复剧集 |
| `app/organize.rs` | 按模板重命名、季文件夹整理、重复剧集合并计划与执行、刮削后自动重命名 |
| `app/cleanup.rs` | 残留文件清理与条目删除；删除只进入废纸篓，废纸篓步骤通过 `Trash` trait 注入，失败时保留记录 |
| `app/locks.rs` | 文件变更锁（见下节） |

刮削分两阶段。网络阶段（匹配、详情、图片字节）不持有任何文件变更锁；写入阶段取得条目所在资料库的锁，在锁内重新读取条目，因此网络阶段期间发生的重命名或删除不会让结果写到旧目录。两阶段都检查取消：取消后已下载但未写入的结果直接丢弃。

## 锁与数据库连接

- 文件变更锁 `MutationLocks`：资料库锁先共享持有全局读写锁，再按 id 排序逐个获取资料库互斥锁，因此不同资料库可以并行变更，跨资料库请求（如一次合并涉及多个资料库）不会互相死锁。根目录互相嵌套的资料库共用锁。`Global` 独占全部资料库，用于任意路径的批量重命名与撤销、残留清理、更换资料库根目录和修改扫描排除项。
- 每次取得锁后都执行媒体操作恢复检查；检查失败时变更被阻止。队列任务在开始前也执行该检查。媒体操作日志登记为“进行中”直到操作结束，恢复只处理已结束或崩溃遗留的日志，不会回滚另一资料库正在进行的合并或重命名。
- 任务队列仍是单一工作者，按入队顺序执行，去重规则不变。刷新、重命名、整理和清理在整个任务期间持有其锁；刮削类任务不持锁运行，只在写入和自动重命名时取锁。直接命令（删除、合并、批量重命名等）因此不再被长时间的网络刮削阻塞，其他资料库的任务也不阻塞它们。
- 数据库：`AppDatabase` 保留一个写连接处理所有写入和事务，另有 3 个只读连接处理查询（WAL，`busy_timeout` 5 秒）。读连接只能看到已提交的数据；事务都在单次 `with_conn` 内完成，不存在在未提交事务中通过读连接读取的路径。内存数据库无法跨连接共享，读取回落到写连接，测试行为不变。

## 界面约束

shadcn/ui 组件源码纳入仓库，由软件自行维护。主题、排版与布局都在本地 CSS 中定义；不依赖外部设计 token 发布。Motion 处理弹窗和任务反馈等动效，并遵循减少动态效果偏好。

UI 组件的可访问行为、领域数据正确性、文件操作安全和原生平台兼容性需要分别验证。入口与命令见[开发指南](../desktop/README.md)，验证边界见[验证指南](perf.md)。
